Gaia Archive

Explaine Gaia here...

The results of Gaia survey has been published in two main types of data: tabular and ancillary. The tabular data can be retrieved easily with TAP queries. The ancillary data are files that contain non-tabular information, such as sprectra and epoch photomerties.

Retrieve tabular data

As other surveys and catalogues, you can retrieve Gaia tabular data from VizieR. But we recommend using Gaia Archive instead of VizieR, because you will have more options. There are multiple ways to access Gaia tabular data. You can directly visit Gaia Archive website and get data from it. You can also use their API with a command-line tool such as curl or a python function such as our own sql2df. Here, we recommend using astroquery.

Before going into details, let's have a look at the Gaia Archive database. Here, we talk about the latest verion, which is Data Release 3. The main table is gaia_source. It contains about about 1.8 billion entries and 153 columns. It is realy huge and querying this table can be very time consuming. A lighter version of this table has been provided named gaia_source_lite. This lighter table has the same number of rows, but instead of 153 columns, it has 52 columns which are the most import ones. So, it is recommended to use gaia_source_lite, unless you look for some information that is not present in it.

Each observed source in Gaia Archive is identified with a source_id. This is a column that is present in almost all tables. Besides the main table, there are lots of other tables that you may be interested in. For example, the astrophysical_parameters table contains one-dimensional astrophysical parameters of about 1.6 billion objects. The galaxy_candidates table describes parameters of about 4.8 million sources considered as galaxy candidates. The qso_candidates table containes more than 6.6 million sources considered as quasars. The table vari_cepheid describes more than 15000 Cepheid stars. If you are interested in Solar system astronomy, you may want to look at the sso_observation table that has information for about 23 million Solar system objects. When using the name of these tables in ADQL queries, you should add gaiadr3. prefix to their names. For example, the name of the main table, when used in an ADQL query, should be gaiadr3.gaia_source.

Regional Search

If you want to retrieve all of the objects in a certain region in the sky, you can use cone_search or query_object. There is no important difference between these two functions. So, we introduce cone_search. You should pass the coordinates of the center of the region to coordinate argument and pass radius of the region to radius argument. There is an optional argument, columns, that lets you specify the columns that you want to be retreieved. If you don't use this argument, all columns be will downloaded. The following example shows how to retrieve all Gaia objects in region indicated by a central point with one arcminute radius. We have chosen just the identifiers and coordinates to be downloaded.

import astropy.units as u
from astropy.coordinates import SkyCoord
from astroquery.gaia import Gaia

c = SkyCoord(ra=202.96, dec=55.19, unit='deg')

job = Gaia.cone_search_async(
    coordinate=c,
    radius=1*u.arcmin,
    columns=['source_id', 'ra', 'dec']
    )

table = job.get_results()
print(table)

Output:

Note that the function cone_search returns an astroquery Job object. You have to apply the .get_results() method on it to get the results as an astropy table. You may also have noticed that one extra column, dist, has been added to the results. This is the angular distance to the center point that we have provided. The results are sorted by the value of this column in ascending order.

You may encounter two limitations. First, the Gaia database is really huge, so, if you define a vast region in sky, you may encounter a timeout error. This is where asynchronous queries become useful. Some of the astroquery functions have asynchronous versions. They are indicated with _async suffix. In the example above, you can use cone_search_async instead of cone_search. Everything else remains the same. When you use asynchronous queries, the server executes your request but it will return the results when they are ready. It does not matter how much time does it take. In the other hand, When you use normal synchronous queries, the results are generated as soon as you send the request. In this case, if it takes more than a cetrain seconds of time, you may encounter timeout error. So, consider to use asynchronous queries when you think that the results may contain thousands rows or it may take a lot of time for the server to execute it.

The second limitation is that you can not filter the results with the cone_search function. All of the Gaia objects that exist in the region will be returned. The best way to overcome this limitation and many other kinds of limitations, is to use Tap queries.

Tap Queries

You can do tap queries on Gaia Archive website, with astroquery, or directly using the api with our own sql2df function. We recommend using astroquery because it enables us to use asynchronous queries.

The function that should be used to execute TAP queries is launch_job. We recommend using its asynchronous version, which is launch_job_async. The example below shows a simple use of this function:

from astroquery.gaia import Gaia

query= """
SELECT TOP 5 source_id, ra, dec
FROM gaiadr3.gaia_source_lite
"""

job = Gaia.launch_job_async(query)

table = job.get_results()
print(table)

The dist columns is missing, because when using TAP queries, only the columns specified in front of the SELECT keyword will be returned. The solution is to use an ADQL function named DISTANCE. It accepts two points as arguments and returns the angular distance between them. We can see this function in our query string, then order the results it.

from astroquery.gaia import Gaia

ra = 202.96
dec = 55.19
r = 1 / 60

query= f"""
SELECT source_id, ra, dec, DISTANCE(POINT(ra, dec), POINT({ra}, {dec})) AS dist
FROM gaiadr3.gaia_source_lite
WHERE CONTAINS(POINT('ICRS', ra, dec), CIRCLE('ICRS', {ra}, {dec}, {r})) = 1
ORDER by dist
"""

job = Gaia.launch_job_async(query)

table = job.get_results()
print(table)

By now, we just did what we have already done with the cone_search function. Let's take a step further and filter the results based on some columns. We also want to make the sky region much larger: instead of a region with 1 arcminute radius, we search in a region with 10 arcdegrees of radius. There are about 100,000 objects in this region, but we want only the objects for which the radial velocity has been measured and their parallax are greater than 50 milliarcseconds, i.e., they are near us.

from astroquery.gaia import Gaia

ra = 202.96
dec = 55.19
r = 10

query= f"""
SELECT source_id, ra, dec, radial_velocity, DISTANCE(POINT(ra, dec), POINT({ra}, {dec})) AS dist
FROM gaiadr3.gaia_source_lite
WHERE radial_velocity IS NOT NULL
AND parallax > 50
AND CONTAINS(POINT('ICRS', ra, dec), CIRCLE('ICRS', {ra}, {dec}, {r})) = 1
ORDER BY dist
"""

job = Gaia.launch_job_async(query)

table = job.get_results()
print(table)

User tables

Gaia Archive lets you upload you own table to their server. This is really helpful because it enables you to combine your table with Gaia tables. There are two ways you can upload a table: as authenticated user or as anonymous user.

If you prefer to communicate with Gaia Archive as an authenticated user, you have to sign up on the Gaia Archive website to have a username and password. Then, use that username and password in your script to login to Gaia Archive before uploading table or sending any kind of request. Authenticated access is not just for uploading tables, you can even perform normal queries, as we have explained above, after loging in with your username and password. The main advantage is that the results of your queries and the tables that you upload will remain on the server forever. For uploading a table as authenticated user, you should use the .upload_table() function. This function has three parameters: upload_resource is the table object that you want to upload; table_name is the name that you give to the table to be used in your queries; table_description is a description about the table. You can upload a table from your hard disk, from a url or from as astropy table. Let's create a simple astropy table and upload it.

from astropy.table import Table
from astroquery.gaia import Gaia

ids = [2653819129231880320, 3854775444998749568, 303312548948736384,
       789430249033567744, 821368171297757952, 3093946285143653248]

types = ['GALAXY', 'GALAXY', 'QSO', 'QSO', 'QSO', 'STAR']

table = Table(data=[ids, types], names=['id', 'type'])

Gaia.login(user='myUsername', password='myPassword')

job = Gaia.upload_table(
    upload_resource=table,
    table_name="my_table",
    table_description="This is for test"
    )

Gaia.logout()

Output:

As we told, if you want to use the .upload_table() function, you must login to Gaia with your username and password. However, you can upload a table on-the-fly anonymously and run a query on it at the same time. Whether you upload a table by loging to the server or upload a table on-the-fly, the objective is alway combine this table with some data from Gaia Archive.

In the example below, we upload our own table anonymously and on-the-fly and we join it to the Gaia main table to retrieve some additional information; here, the coordinates. Note that we use the upload_resource argument of the launch_job function to upload our table. You should also pay attention to the naming convention of uploaded tables. We give a name to our table with the upload_table_name argument. When you upload a table on-the-fly, the full name would be tap_upload.TableName. In our case, name of the table is my_table, so to access it in the query, the full name will be tap_upload.my_table. 

from astropy.table import Table
from astroquery.gaia import Gaia

ids = [2653819129231880320, 3854775444998749568, 303312548948736384,
       789430249033567744, 821368171297757952, 3093946285143653248]
types = ['GALAXY', 'GALAXY', 'QSO', 'QSO', 'QSO', 'STAR']
table = Table(data=[ids, types], names=['id', 'type'])

query = """
SELECT source_id, type, ra, dec
FROM gaiadr3.gaia_source_lite AS gaia
JOIN tap_upload.my_table AS my
ON my.id=gaia.source_id
"""

job = Gaia.launch_job_async(
    query=query,
    upload_resource=table,
    upload_table_name="my_table"
    )

tb = job.get_results()
print(tb)

Cross Match

The main reason for uploading tables to the Gaia Archive is to be able to combine our data with that of the Gaia catalogue. Our uploading table may be a simple table as in the above examples, or it may be a complete catalogue. Cross-math is the action of combining catalogues.

In the above examples, both tables, our own table and the Gaia table, had a commun column - id in our table and source_id in the Gaia table. This helped us to combine the tables very easily. In the real world, this is not alway the case. Sometimes, the catalogue that you want to combine with Gaia has a different identifier. It is not always easy to find out which object of this catalogue corresponds to an object in Gaia catalogue. Let's starts with the easy part.

Pre-computed cross-matches

The Gaia Archive has already prepared some tables to help users combine Gaia catalogue with some popular external catalogues, such as allWISE, Hipparcos, 2MASS, SDSS, etc. You can find cross-match tables on the Gaia Archive website, SEARCH tab, then Advanced (ADQL) tab, under Cross match namespace for each data release. For each external catalogue, Gaia Archive has probided two or three tables in the Cross match namespace. Typically, we'll use the one with _best_neighbour suffix. This is a table that lists each matched Gaia object with its best neighbour in the external catalogue. For example, if we want to combine Gaia with SDSS DR3, we will use the table gaiadr3.sdssdr13_best_neighbour in our query. This table has several columns, but two columns are essential for us: source_id which is the identifier of the object in Gaia, and original_ext_source_id which is the identifier of the object in the external catalogue, which is here, SDSS DR13.

As a very simple example, suppose that you have the identifiers of some objects in the SDSS 13 catalogue and you want to find their identifiers in Gaia DR3:

from astroquery.gaia import Gaia

sdss_ids = ('1237645879551066262', '1237645879578460255',
            '1237645879578460271', '1237645941291614227')

query = f"""
SELECT source_id, original_ext_source_id
FROM gaiadr3.sdssdr13_best_neighbour
WHERE original_ext_source_id IN {sdss_ids}
"""

job = Gaia.launch_job(query)

table = job.get_results()
print(table)

Output:

As another example, let's retrieve all Gaia objects in a sky region that have best neighbours is the SDSS DR13 catalogue. We want to get their identifiers in Gaia and SDSS as well as their coordinates.

from astroquery.gaia import Gaia

Geometric cross math

For cross-matching some external catalogues that have not pre-computed tables in Gaia Archive, we should use geometric cross-math. This means that we match objects from two catalogues based on their angular distance. For example, we may decide that if the coordinates of the two objects from the two catalogues have an angular distance less than 1 arcsecond, they are potentially the same object.

Let's show this with a simple example. We need an external catalogue to combine with Gaia. In the script below we retrieve all SDSS objects in a sky region with radius of 2 arcminutes then we save the results in a file on disk and we name it 'sdss_region.fits'. Later we will see how to download from SDSS, but for now, this is just a simple cone search. We just keep three columns from the resulting table.

import astropy.units as u
from astropy.coordinates import SkyCoord
from astropy.table import Table
from astroquery.sdss import SDSS

c = SkyCoord(ra=179.689, dec=-0.454, unit='deg')
s_table = SDSS.query_region(c, radius=2*u.arcmin)
s_table = Table(s_table[['objid', 'ra', 'dec']], dtype=[str, float, float])
s_table.pprint(max_lines=5)
s_table.write('sdss_region.fits')

Now, we read this table from the disk and upload it to Gaia Archive server using the launch_job_async function along with the cross-match query. In the query we want to join our SDSS table with Gaia, but there is no common column in these two tables So, instead of joining based on common columns, we should do JOIN ON DISTANCE. Note that DISTANCE is an ADQL function. It accepts as its arguments the coordinates of two points. This function returns the angular distance of two points in degrees. The condition of the cross-match that we have chosen is so that if the distance between the objects of the two tables is less than 0.00028 degrees, i.e. 1 arcsecond, then select those objects as matchin objects.

from astroquery.gaia import Gaia
from astropy.table import Table

s_table = Table.read('sdss_region.fits')

query= """
SELECT sdss.objid, gaia.source_id, gaia.ra, gaia.dec
FROM tap_upload.my_sdss AS sdss
JOIN gaiadr3.gaia_source_lite AS gaia
ON DISTANCE(sdss.ra, sdss.dec, gaia.ra, gaia.dec) < 0.00028
"""

job = Gaia.launch_job_async(
    query=query,
    upload_resource=s_table,
    upload_table_name="my_sdss"
    )

table = job.get_results()
table.pprint(max_lines=5)

The results show that there have been 67 potential matching objects. Note that the last row and the row above it are two different SDSS objects, but one single object in Gaia. This is why you should consider the results as potentially matching objects and further analysis may be nessesary.

The minimum angular distance that we have chosen for the join condition is one arcsecond. You may think that if we decrease this number, we would get more precise results. That's true, but, there's still something you can consider if you want really precise results. The reference epoch of these two catalogues are not the same. The reference epoch of SDSS is J2000, while, that of Gaia DR3 is J2016. There is a very little difference between these two epochs, but if you consider that, you increase the precision.

To take into account the difference of epoch, we should convert coordinates of one of the tables to the epoch of the other table. The ADQL running on Gaia Archive server has a useful function that does this task: EPOCH_PROP_POS. This function accepts coordinates, parallax, proper motion, radial velocity, initial epoch and final epoch as its arguments and returns the propagated position in in radians in the final epoch. The signature of this function is as follow:

EPOCH_PROP_POS(ra, dec, plx, pmra, pmdec, rv, T0, T1)

Where, arguments and their units are as follow:

ra    : Right Ascension (deg)
dec   : Declination (deg)
plx   : Parallax (mas)
pmra  : Proper Motion in Right Ascension (mas/yr)
pmdec : Proper Motion in Declination (mas/yr)
rv    : Radial Velocity (km/s)
T0    : Reference Julian Epoch (yr)
T1    : Final Julian Epoch (yr)

The returned value of EPOCH_PROP_POS function is a string representation of the coordinates. We can extract RA and DEC from this string using two ADQL functions: COORD1 and COORD2. So, the ADQL that we used in the last example should change to this:

SELECT sdss.objid, gaia.source_id, gaia.ra, gaia.dec
FROM tap_upload.my_sdss AS sdss
JOIN gaiadr3.gaia_source_lite AS gaia
ON
DISTANCE(
    sdss.ra,
    sdss.dec,
    COORD1(EPOCH_PROP_POS(gaia.ra, gaia.dec, gaia.parallax, gaia.pmra, gaia.pmdec, gaia.radial_velocity, 2016, 2000)),
    COORD2(EPOCH_PROP_POS(gaia.ra, gaia.dec, gaia.parallax, gaia.pmra, gaia.pmdec, gaia.radial_velocity, 2016, 2000))
) < 0.00028

I don't recommend running sending this query to the Gaia server, because it takes a lot of time to be executed. If fact, the EPOCH_PROP_POS function should be run on every single row in Gaia main table and it is a time consuming function. A tricky solution is to limit the number of the rows on which this function should be run. In our example, all the objects are located in a sky region limited by raduis of 2 arcmintes. So, instead of joining our SDSS table to the whole Gaia main table, we can first extract all of the Gaia objects in that region and then join our SDSS table with this limited table. We extract this limited table in a subquery. To make sure that we don't miss any Gaia object due to the epoch propagated, we choose the region radius a little larger than 2 arcminutes. I choosed 2.5 arcminutes.

from astropy.table import Table
from astroquery.gaia import Gaia

s_table = Table.read('sdss_region.fits')

ra = 179.689
dec = -0.454
r = 2.5 * (1/60)

query= f"""
SELECT sdss.objid, subq.source_id, subq.ra, subq.dec
FROM tap_upload.my_sdss AS sdss
JOIN ( SELECT source_id, ra, dec, parallax, pmra, pmdec, radial_velocity
       FROM gaiadr3.gaia_source_lite
       WHERE CONTAINS(POINT('ICRS', ra, dec), CIRCLE('ICRS', {ra}, {dec}, {r})) = 1
     ) AS subq ON
DISTANCE(
    sdss.ra,
    sdss.dec,
    COORD1(EPOCH_PROP_POS(subq.ra, subq.dec, subq.parallax, subq.pmra, subq.pmdec, subq.radial_velocity, 2016, 2000)),
    COORD2(EPOCH_PROP_POS(subq.ra, subq.dec, subq.parallax, subq.pmra, subq.pmdec, subq.radial_velocity, 2016, 2000))
) < 0.00001
"""

job = Gaia.launch_job_async(
    query=query,
    upload_resource=s_table,
    upload_table_name="my_sdss"
    )

table = job.get_results()
table.pprint(max_lines=5)

Download ancillary data with DataLink

For some of the objects, the Gaia survey provides some additional non-tabular information that are presented in separate files. These are known as ancillary data. These additional data are epoch photometry, spectra and probability distributions for some parameters. The ancillary data can not be retrieved by TAP queries explaned above. To download these types of data, you have to use a special data access protocol, called DataLink.

EPOCH_PHOTOMETRY : Light curve of object in G, BP, and RP bands
XP_CONTINUOUS    : Mean BP/RP spectra based on the continuous representation
XP_SAMPLED       : Mean BP/RP externally-calibrated and sampled spectra
RVS              : Mean RVS normalised and sampled spectra
MCMC_GSPPHOT     : MCMC samples for posterior probability distribution of all parameters derived from GSP-Phot
MCMC_MSC         : MCMC samples for posterior probability distribution of all parameters derived from MSC

The acronyms used above are as follows: MCMC for Monte-Carlo Markov Chain, GSP-Phot for General Stellar Parametrizer from Photometry, and MSC for Multiple Star Classifier. We don't explain all of them, we'll just talk about the first three ones.

Note that not every single Gaia object has ancillary data. To check if an object has each of these types of data you should use the main Gaia table: gaia_source or gaia_source_lite. In these tables, there are columns with has_ prefix that is of boolean type and indicates if the object contains each of the above-mentioned ancillary data. For example, if the value of the column has_xp_continuous is true. Let's get some objects which have all of the first three ancillary typed mentioned above:

from astroquery.gaia import Gaia

query= """
select TOP 5 source_id
FROM gaiadr3.gaia_source_lite
where has_epoch_photometry = 't'
AND has_xp_sampled = 't'
AND has_rvs = 't'
"""

job = Gaia.launch_job(query)

table = job.get_results()
table.pprint()

You saw that we can use load_data function to retrieve ancillary data. In fact, you can download data for multiple objects at the same time with this function by passing their identifiers as a list to the ids argument. You can also indicate which type of ancillary data you want to be downloaded using the retrieval_type argument. If you don't provide this argument, or if you give it the string ALL, all available ancillary data will be downloaded. If you are only interesed in a certain type, pass it as a string to this argument as shown in the example below. Let's say we want just EPOCH_PHOTOMETRY of the objects.

>>> dc = Gaia.load_data(
	ids=[4251837548057346048, 4251838437014014976, 4251838681929094912],
	retrieval_type='EPOCH_PHOTOMETRY'
	)
>>> for k in dc.keys():
	print(k)
